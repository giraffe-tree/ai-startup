# 技术债审计

**项目**: DocFlow AI
**审计日期**: 2026-05-26
**审计范围**: MVP 代码库（Next.js + PostgreSQL + OpenAI API）

---

## 结构性弱点

### 1. OpenAI 调用无抽象层
所有合同解析逻辑直接在 API route 里调用 `openai.chat.completions.create()`，prompt 字符串散落在 5 个不同文件中。切换模型（GPT-4o → Claude）或调整 prompt 需要改多处，且无法统一测试。

### 2. 文档处理无任务队列
用户上传 PDF 后，文本提取和 AI 分析在同一个 HTTP 请求里同步完成。超过 30 页的合同会触发 Vercel 函数 10 秒超时，已有 3 个真实用户反馈"上传失败"。

### 3. 数据库 Schema 无版本管理
直接在生产库手跑 `ALTER TABLE`，没有迁移记录。现有 `contracts` 表缺少软删除字段（`deleted_at`），删除合同是物理删除，无法恢复。

### 4. 认证逻辑与业务逻辑耦合
`/api/contracts/[id]/route.ts` 里手写 session 校验，而不是用中间件。三个 API 文件各自实现了略有不同的鉴权代码，存在越权访问风险（未测试跨租户隔离）。

### 5. 前端无错误边界
React 组件未设置 Error Boundary，AI 分析返回格式异常时整页白屏，用户无法重试。

## 测试覆盖缺口

| 模块 | 当前覆盖率 | 风险说明 |
|------|-----------|---------|
| 合同解析 prompt 逻辑 | 0% | 完全依赖人工测试，prompt 改动无回归 |
| 跨租户数据隔离 | 0% | 律所 A 能否读到律所 B 的合同？未验证 |
| PDF 提取边界情况 | ~20% | 扫描件、加密 PDF、超 100 页未测试 |
| API 鉴权 | ~40% | 正常路径有测试，异常 token 场景缺失 |
| 数据库迁移 | 0% | 无迁移脚本，无回滚测试 |

## 修复排期

### P0 — 下个版本前必须修复（1-2 周内）

**P0-1：修复跨租户数据隔离**
- 问题：律所客户的核心信任基础。一旦泄露，产品即死。
- 修复：所有数据库查询加 `WHERE org_id = :current_org_id`；写集成测试用两个测试租户互访验证。
- 工作量：3 天

**P0-2：引入任务队列解决超时**
- 问题：大合同上传失败直接影响付费用户体验。
- 修复：用 `pg-boss`（利用现有 PostgreSQL）做任务队列，文档上传立即返回 job_id，前端轮询状态。
- 工作量：4 天

**P0-3：统一鉴权中间件**
- 问题：散落的鉴权代码是安全漏洞温床。
- 修复：抽取 `withAuth` 高阶函数，所有 API route 统一使用。
- 工作量：2 天

### P1 — 可与功能开发并行（1 个月内）

**P1-1：OpenAI 调用抽象层**
- 目标：所有 prompt 集中到 `lib/ai/` 目录，统一接口，方便后续切换模型和 A/B 测试 prompt。
- 工作量：3 天

**P1-2：数据库迁移工具**
- 工具：引入 `drizzle-orm` 或 `node-postgres-migrate`，补录所有现有 schema 变更为迁移文件。
- 工作量：2 天

**P1-3：前端错误边界 + 重试机制**
- 在合同分析、文档上传组件加 Error Boundary，AI 返回格式异常时显示"分析失败，点击重试"。
- 工作量：1 天

**P1-4：合同解析核心路径单元测试**
- 针对 prompt 输出格式写 Jest 测试（mock OpenAI 返回），覆盖"正常合同 / 缺失条款 / 格式异常"三种场景。
- 工作量：3 天

### P2 — 可接受的持续债务（季度内跟踪）

**P2-1：软删除**
- 现状：物理删除可接受，但律所有保留记录的合规需求，长期需补。

**P2-2：日志结构化**
- 现状：`console.log` 散落各处，未接入结构化日志（如 Pino）。上线后排查问题困难。

**P2-3：前端组件测试**
- 现状：React 组件无测试，暂时接受，待产品形态稳定后补充。

## CLAUDE.md 补录事项

以下 MVP 阶段口头约定需写入 `mvp/CLAUDE.md`：
- 所有数据库查询必须携带 `org_id` 过滤（多租户强约束）
- OpenAI 调用统一走 `lib/ai/` 目录，禁止在 API route 直接调用
- 任务队列 job 状态字段：`pending / processing / completed / failed`
